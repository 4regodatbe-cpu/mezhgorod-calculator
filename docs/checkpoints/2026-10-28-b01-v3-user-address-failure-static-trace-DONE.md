## Проверенная цепочка и границы
- `app/v3/page.tsx` использует `app/v2/components/calculator-form.tsx` и `address-field.tsx`.
- `address-field.tsx`: debounce 350 мс, POST `/r`; cleanup отменяет прежний запрос; ответ с `!ok` переводится в UI error. Ранее опубликованная B03 фиксация очистки/повторного фокуса присутствует (blob `75bbf3391bcfd8bf777ce6b278c3fb78cff56981`).
- `app/r/route.ts`→`app/api/suggest/route.ts`→`lib/address-search-service.ts`→`lib/photon-request-pool.ts`/`lib/photon-fetch.ts`→`rankPhotonFeatures`.
- `photonSearchUrls("Донецк")`: 7 отдельных URL (глобальный, UA, RU и 4 bbox-территории); для «Волноваха» также 7 при отсутствии отдельного алиаса; индекс `data/ruwiki-settlement-index.json` содержит обе записи с area=dnr. Это **проверка исходников/индекса**, не live-получение подсказок.
- Пул активен (`data/toll-feature-switches.json`), допускает **2 одновременных** upstream запросa, остальное очередью. Весь запрос ограничен **20 000 мс**, каждый upstream — до **20 000 мс**. При семи URL и медленном upstream возможно истечение общего бюджета до обработки всех вариантов. Доказательство: в сохранённых проверках был валидный Photon-ответ за 11,27 с; при двух параллельных запросах это позволяет выполнить только первую волну до 20 с. **Это установленный архитектурный риск, но не установленная единственная причина данного публичного отказа**.
- `scripts/address-search-runtime-probe.mjs` устанавливает собственный лимит 20 000 мс, такой же как у коллектора. Гонка двух дедлайнов может превращать завершение коллектора на границе в `QUERY_TIMEOUT`, не показывая частичный результат.
- `app/api/suggest/route.ts` возвращает HTTP 502, когда все upstream-варианты отклонены. `addressCitySnapshot` отключён (`false`); сохранённый проверенный снимок содержит два Донецка, Краснодар и Ростов, **но не Волноваху**, и заканчивается 31.10.2026. Включать снимок как универсальный fallback нельзя.
- Исторический фактический B01-провал: один локальный запрос Анапа→/r вернул 502 и 7 network_error (`docs/checkpoints/2026-10-28-b03-b01-live-result.md`). Отдельный более поздний тест с корректным proxy-aware Node дал 200 для Анапы и Донецка (`docs/checkpoints/2026-10-28-b01-proxy-live-flow-result.md`). Следовательно, ни постоянный отказ Photon, ни клиентская ошибка не доказаны как универсальная причина.
- Попытка читать Vercel production logs за 12 ч отклонена ограничением хранения Hobby; за 30 мин критерий `address_search` не дал записей. Это **не** подтверждение отсутствия инцидентов. Внешний GET Волноваха через web-инструмент был недоступен для проверки; ответ API не получен.

## Вывод / дальнейший блок
**Причина конкретного пользовательского 502 остаётся не локализованной до сетевого события**. Серверный узкий участок — связка fan-out (7 вариантов) + пул(2) + бюджет(20с); её необходимо проверить на детерминированной модели upstream с задержкой и ошибками. Следующая допустимая точечная работа: снять bounded evidence для `Донецк` и `Волноваха` отдельно, разработать минимальное поэтапное выполнение приоритетных запросов/ранний возврат корректного результата без потери приоритета ДНР, добавить offline тесты тайминга, координат, отмены и partial failure. Затем mandatory offline gate/TS/build/CI и защищённый Preview с реальным Android/E2E.

**Ограничение:** изменения в `lib/**` или `scripts/*.test.ts` вызовут workflow `special-territory-policy.yml` с широкими live-проверками 50 городов, Яндекс и др. В задаче запрещён запуск дополнительного широкого аудита без отдельного разрешения. Исключение B03 относится только к AddressField; не использовать его для backend и не менять/обходить классификатор. Поэтому в данном блоке **не вносились изменения в runtime, тесты или CI, не создавался Preview**. До публикации backend фикса необходимо отдельно согласовать допустимый штатный CI-режим либо выполнить уже разрешённую проверку; не обходить контроль путём записи в неохваченный путь.
