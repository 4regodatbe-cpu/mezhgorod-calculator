# Межгород Calc — handoff и архитектурные инварианты

Этот файл нужен следующему разработчику, новому чату или ревьюеру, чтобы быстро понять, как устроен текущий production-контур и какие правила нельзя случайно нарушить.

## 1. Какая версия считается основной

- Публичный основной интерфейс: `/v2`.
- Корневой `/` должен перенаправлять на `/v2`.
- Android 2.0 открывает `/v2`.
- `/v3` временно не развиваем и не используем как площадку для новых продуктовых изменений. Новая логика маршрутов и кэширования сначала внедряется в V2.

## 2. Главный принцип платных дорог

Сумма платных дорог не должна собираться по принципу «нашли первый известный платный участок — показали его как итог маршрута».

Для длинных маршрутов стоимость складывается из независимых компонентов. В текущем контуре используются отдельные движки/детекторы для семейств дорог, включая М-4/А-289, М-11, М-12 и ЦКАД.

Критический инвариант:

- если маршрут содержит платный компонент, но его стоимость не удалось полностью и надёжно определить, весь итог платных дорог должен перейти в `pricingStatus=unknown`;
- при `unknown` сумма обязана оставаться `null`;
- `unknown` никогда нельзя превращать в `0 ₽`;
- частичная сумма не должна выдаваться как полная стоимость маршрута.

## 3. Provider consistency

Геометрия маршрута, дорожные доказательства и расчёт платных компонентов должны относиться к одному и тому же выбранному live-маршруту.

Нельзя использовать дорожное доказательство Valhalla для маршрута, который был выбран от OSRM/BRouter, только потому что Valhalla тоже вернула похожий маршрут.

Если нужного доказательства для выбранного маршрута нет — безопаснее перейти в `unknown`, чем склеить данные разных маршрутов.

## 4. Бесплатный маршрут

`free` и `freeCandidate` — не одно и то же.

- `free` — подтверждённый маршрут без платных дорог;
- `freeCandidate` — кандидат, который пока не прошёл достаточную проверку.

Интерфейс и телеметрия не должны называть `freeCandidate` подтверждённым бесплатным маршрутом.

## 5. Контрольные маршруты

Особенно важные regression/live кейсы:

- Москва — Казань: М-12;
- Ейск — Москва: М-4;
- Майкоп — Москва: М-4;
- Краснодар — Санкт-Петербург: композиция нескольких платных систем;
- Голубицкая — Санкт-Петербург: длинная композиция;
- Витязево — Санкт-Петербург: длинная композиция;
- Казань — Ялта: комбинация М-12 и южных платных участков;
- Тверь — Адлер: полный южный маршрут;
- Москва — Краснодар и Москва — Сочи: контроль бесплатного альтернативного маршрута.

Исторические ошибки, которые не должны вернуться:

- Москва — Казань = `0 ₽`;
- Ейск — Москва = `0 ₽`;
- Майкоп — Москва = `0 ₽`;
- длинный юг → Санкт-Петербург с ценой только одного найденного участка.

## 6. Проверки перед изменением main

Обязательный основной gate: `.github/workflows/calculator-final-gate.yml`.

Он должен охватывать как минимум:

- static production-readiness;
- static civilian corridor policy;
- toll regression corpus;
- route-quality corpus;
- golden route corpus;
- verified-route database integrity;
- tariff freshness;
- М-12 recovery;
- systemic composition;
- ЦКАД;
- М-4 traversal;
- М-11;
- majority route selection;
- lint;
- production build;
- API smoke;
- live free-route truth;
- live user-route audit;
- daily monitor contract.

Если код меняет расчёт маршрута, платные дороги, API, V2 UI, телеметрию или проверенную базу, соответствующая regression-проверка должна меняться вместе с кодом.

## 7. Телеметрия и приватность

Статистика должна оставаться обезличенной.

Не отправлять в хранилище точные адреса, координаты пассажира или другие лишние данные.

Целевой минимум статистики маршрута:

- город/регион A;
- город/регион B;
- расстояние;
- эффективный тариф;
- итоговая стоимость.

Перед записью местоположение должно быть укрупнено до города/региона. `pricingStatus=unknown` нельзя записывать как нулевую стоимость платной дороги.

## 8. Проверенные маршруты в V2

Целевая архитектура V2: проверенная геометрия маршрута и тарифы платных дорог имеют разные сроки жизни.

После того как маршрут надёжно сверён, можно сохранять его маршрутный snapshot: точки, выбранный коридор, геометрию, расстояние, время, подтверждённую бесплатную альтернативу и известные дорожные семейства.

При повторном идентичном запросе V2 должен использовать snapshot без повторного запуска всех внешних маршрутизаторов, если маршрут не инвалидирован. При этом стоимость платных дорог пересчитывается по актуальной тарифной базе отдельно.

Изменение цены платной дороги само по себе не должно инвалидировать геометрию маршрута.

Полную повторную проверку маршрута запускаем при изменении A/B, обязательного коридора, логики маршрутизации, дорожного графа либо при обнаруженном контрольным монитором существенном расхождении.

## 9. Статическая политика южных и специальных направлений

Логика выбора коридора не должна каждый раз вычислять «выгоднее ли сейчас ехать через Крым или Ростов». Для production используется заранее проверяемая статическая матрица `lib/route-corridors.ts`.

Основные правила:

- южная исходная зона задаётся явным whitelist населённых пунктов;
- для каждого специального направления заранее назначается гражданский коридор;
- runtime выполняет lookup, а не динамическое сравнение вариантов;
- не использовать оперативные/тактические данные и линию боевого соприкосновения как источник маршрутизации;
- пограничные направления, которые ещё не сверены, должны переходить в `manual_review`, а не получать случайный маршрут;
- Краснодар/южное побережье → Мелитополь: `crimea_dzhankoy`;
- Крым/юг → Мариуполь/Донецкое направление: `m4_dnr`;
- Краснодар/юг → Луганское направление: `m4_lnr`;
- обратный маршрут сохраняет тот же назначенный коридор;
- специальные направления автоматически используют двойную тарификацию;
- базовая специальная сетка: Стандарт 70 ₽/км, Комфорт 80 ₽/км, Комфорт+ 90 ₽/км, Минивэн 110 ₽/км;
- эти значения видимы пользователю самого калькулятора и должны оставаться редактируемыми;
- скрытие внутренней тарифной разбивки от пассажира относится к будущему landing page, а не к V2-калькулятору.

Тест: `scripts/route-corridor-policy-test.ts`.

## 10. Тарифы пользователя

Пользовательские тарифы и наценки должны:

- иметь явные разумные границы;
- безопасно восстанавливаться из `localStorage`;
- не превращать отсутствующее значение в неправильный минимум из-за `Number(null) === 0`;
- не позволять `NaN`, `Infinity` или аномально большие значения попадать в расчёт.

## 11. Диагностические API

Debug-endpoints не должны быть открыты в production без защиты.

На Vercel диагностические endpoints должны требовать `CALCULATOR_DEBUG_TOKEN` через `x-calculator-debug-token` либо быть недоступны.

## 12. Vercel и CI

Не использовать Vercel preview как единственный способ проверки изменений.

Рабочая ветка `fix-systemic-toll-composition` специально не должна расходовать preview-deploy на каждый коммит. Основная проверка выполняется в GitHub CI на локально поднятой production-сборке.

Это сделано из-за лимита бесплатных deployments и для уменьшения количества бессмысленных внешних сборок.

## 13. Как вносить изменения

Предпочтительный порядок:

1. Найти системную причину, а не латать один маршрут.
2. Исправить весь класс ошибки, если это безопасно.
3. Добавить regression, который зафиксирует найденный инвариант.
4. Прогнать lint/build/static gates.
5. Прогнать live-аудит реальных маршрутов.
6. Только после зелёного gate рассматривать merge/deploy.

Не удалять существующий gate только ради прохождения CI. Если тест стал красным, сначала выяснить: устарел тест или появилась реальная регрессия.

## 14. Коммиты

Commit message должен объяснять смысл изменения, а не быть `fix`, `update` или `changes`.

Хороший формат:

- `Keep toll evidence bound to selected route provider`
- `Fail closed on incomplete toll composition`
- `Gate verified route database integrity`

По истории коммитов следующий разработчик должен понимать, почему правило появилось.
