# Обязательное сохранение каждого небольшого шага

Решение пользователя от 15.10.2026, уточнённое в 19:00 МСК. Действует во всех следующих чатах и для всех исполнителей проекта. Это инструкция репозитория, а не зависимость от памяти чата.

## Единица сохранения

Отдельным небольшим шагом считается одно логически законченное изменение кода/данных/инструкции, один тестовый запуск, один маршрут с его исходными ответами, либо одна операция восстановления. Не накапливать десятки маршрутов или несколько исправлений до общего сохранения.

Для каждого такого шага создавать отдельный файл `docs/checkpoints/YYYY-MM-DD-HHMMSS-short-name.md`. Связанные изменения нескольких файлов допустимы в одном checkpoint, если решают одну неделимую задачу. Новые результаты добавлять новым checkpoint или датированным дополнением; историю не стирать.

## Порядок работы

1. В начале сверить branch/commit/PR и `docs/WORK_STATE.md`, найти последний подтверждённо сохранённый checkpoint. Использовать checkout текущей сессии, а не рабочий каталог другого чата.
2. До длительной операции сохранить STARTED: точные входные параметры, цель, ожидаемые выходы, способы продолжения/повтора и текущий исходный commit. Незавершённый шаг не считать выполненным.
3. Выполнить только один небольшой шаг. Исходные сетевые ответы и промежуточный progress сохранять по мере получения; не держать всё только в памяти процесса. Все исходники и результаты должны иметь ссылки и контрольные суммы, когда это применимо.
4. В отдельном checkpoint описать что изменено, зачем и где; принятое решение; команды; фактические результаты/ошибки; выполненные и ещё не выполненные проверки; ограничения; branch/base commit/PR; один точный следующий шаг.
5. Обновить короткий `docs/WORK_STATE.md`, релевантный WORK_LOG/NEXT_STEPS ссылками. Не подменять подробное описание сообщением в чат.
6. Сохранить файлы и evidence локальным Git commit, затем в разрешённой рабочей ветке GitHub. Проверить фактический remote branch head и соответствие tree/файлов. Только после этого переходить к следующему независимому шагу.
7. Если сохранение не прошло, не расширять работу и не запускать новую серию. Зафиксировать точный blocker, сохранить переносимое состояние доступным способом и сообщить пользователю. Не менять transport для обхода явного запрета доступа.

## Когда шаг считается надёжно сохранённым

Одновременно доступны код/данные/описание, есть commit, commit достижим из разрешённой GitHub-ветки, а branch head проверен после обновления. Загрузка одних blob/tree объектов без branch reference, локальный commit в временном каталоге, запись в памяти инструмента или сообщение в чат этим требованиям **не соответствуют**.

Если remote commit создаётся через GitHub connector, сопоставить tree с локальным деревом либо проверить SHA каждого перенесённого объекта. Для больших base64-данных проверять полноту чтения и SHA; при ограничении вывода читать порциями. Не объявлять передачу завершённой по числу отправленных запросов.

## Шаблон отдельной записи

- Статус: STARTED / DONE / FAILED / BLOCKED; дата/время МСК.
- Задача и исходные входы; parent/source commit, branch, PR.
- Что сделано, зачем, затронутые пути и решения.
- Команды, реальные результаты, evidence paths и SHA.
- Что проверено, что не проверено; ошибки и ограничения.
- Состояние durable-сохранения; фактический remote commit фиксируется проверкой Git/следующей записью, без самоссылочного SHA внутри собственного commit.
- Один следующий шаг и условия безопасного повтора.

## Уточнение эффективности от 16.10.2026 21:51 МСК

Применять [правила разбора причин и отчётности](WORKFLOW_RULES.md). Короткий локальный разбор уже сохранённых данных не требует отдельного STARTED commit: один DONE/FAILED checkpoint сохраняется по завершении этого ограниченного шага. STARTED по-прежнему нужен до длительного сетевого запроса, тестового процесса или другой операции с риском прерывания. Каждый законченный шаг всё равно должен иметь commit, сохранение в разрешённой ветке и readback до следующего независимого шага.

Для повторного случая сначала проверять исключения из уже установленной причины. Полный повтор допустим при конкретном отличии входов, геометрии, тарифицируемого продукта, версии данных/кода или недостаточном исходном evidence. Не выдавать такую проверку исключений за новый live/full replay. Для документации проверять содержимое, ссылки и формат; новые широкие тесты запускать при требовании gate либо конкретном изменении риска. Обязательные проверки кода и правило единственного writer сохраняются.

## Ограничения

Правило не ослабляет fail-closed тарификацию и не разрешает merge, Production, удаление данных или обход разрешений. Пройденный unit test не означает правильность тарифа; сохранённый manifest не заменяет потерянный raw capture. Сводные отчёты пользователю остаются краткими, хотя записи внутри проекта подробные.


## Уточнение пользователя — 17.10.2026 15:00 МСК: пакетные проверки

Для повторяющихся случаев одной уже установленной причины пользователь разрешил и поручил пакетную проверку. Один ограниченный пакет — одна единица сохранения: STARTED до длительного запуска; отдельный результат по каждому фактически проверенному случаю и progress для восстановления; один итоговый checkpoint/commit/readback на пакет. Поштучные74 commits/CI не требуются. Это уточняет прежнее требование поштучного commit именно для таких разрешённых пакетов; отдельные изменения независимых причин не объединять. Использовать сохранённые capture, новые live/full replay только при конкретном отличии или недостаточном evidence. Проверенные, рассчитанные компоненты и подтверждённые полные тарифы считать отдельно. Старый завершённый формальный план хранить в истории, но его процент больше не включать в текущие отчёты пользователю.


## Восстановление после зависания — 17.10.2026 23:07 МСК

Применять раздел «После зависания» в [WORKFLOW_RULES.md](WORKFLOW_RULES.md). В recovery checkpoint записывать последний подтверждённо сохранённый шаг, фактические локальные/удалённые результаты и место остановки; разбить незавершённый остаток последней задачи на последовательные части с входами, лимитами, выходами и критериями готовности. После каждой части — фактические проверки, commit/readback и следующий шаг; при повторной остановке дробить только оставшуюся часть. Сохранять per-case progress разрешённого пакета, без повторного запуска готовых случаев. При сбое передачи восстанавливать сохранение готовых файлов, а не повторять вычисления.
