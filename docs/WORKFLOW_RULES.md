# Работа по причинам, ограничение объёма и отчётность

Утверждено пользователем 16.10.2026 21:51 МСК. Это действующее уточнение для следующих чатов и автоматического продолжения. Связанные обязательства: [AGENTS.md](../AGENTS.md), [сохранение шагов](CHECKPOINT_PROTOCOL.md), [текущее состояние](WORK_STATE.md).

## Четыре правила пользователя

1. Разбирать находки по причине и влиянию на пользователя. Повторяющиеся случаи проверять на исключения, не проходить заново целиком без конкретной причины.
2. Для каждой оценённой причины фиксировать понятный итог: **исправлена и проверена**, **не воспроизвелась**, **заблокирована отсутствием надёжных данных**, **отложена**.
3. Не добавлять подэтапы ради количества. Из больших файлов читать нужные поля/диапазоны; подробные логи и raw не копировать в контекст.
4. В отчётах процент из формального плана указывать отдельно от нерешённых причин, фактического числа проверок и подтверждённости тарифов.

## Как разбирать одну причину

Запись причины содержит ID, влияние на пользовательский расчёт, исходные SHA/версию кода, представительный случай, доказательство общей причины, проверенные исключения, итог и точный следующий шаг. Для исправления указать фактические regression/focused/full checks согласно AGENTS; для «не воспроизвелась» — проверенные входы и текущий результат; для блокировки — каких независимых данных не хватает; для отложения — основание и условие возвращения. Текущий незаконченный разбор отмечать как IN_PROGRESS, не подменять его одним из завершённых итогов. Старые поля/статусы журналов сохранять; новую классификацию указывать явно, например `causeReviewStatus`.

В повторяющемся случае сначала сравнить необходимые инварианты с установленной причиной: полноту и идентичность сохранённого capture, даты отправления, выбранную геометрию/граничные события, тарифный продукт и версию кода/источника. Полный replay или новая live-съёмка нужны, когда есть конкретное отличие либо исходные evidence неполны. Одно совпавшее название дороги или один образец не доказывает все остальные случаи. Каждую реально выполненную проверку исключения сохранять ограниченным checkpoint; отдельно считать подробные разборы, проверки исключений, replay-профили и live-запросы. Счётчик не увеличивать за непросмотренные случаи.

Отсутствие независимого доказательства границы/тарифа может завершить диагностический разбор статусом блокировки; это не исправление и не подтверждение тарифа. Unknown не равен нулю, subtotal не является полным итогом. Тарификация всей поездки определяется отправлением; междорожные векторы остаются отложены.

## Границы плана и процент

- [Два этапа аудита](../experiments/nationwide-tolls/TWO_STAGE_AUDIT_PLAN.md) делят 309 оставшихся случаев на 155 и 154 (до этого 31 из 340 были сохранены).
- [20-частный JSON-план](../experiments/nationwide-tolls/SMALL_PARTS_PLAN.json): части 3–10 включают первые 155, части 11–18 — следующие 154, часть 19 — причины/исправления, часть 20 — обязательная итоговая проверка и передача состояния.
- Формула остаётся `100 * полностью завершённые части / 20`, без частичного кредита и новых весов. На момент решения завершено 18/20, то есть **90% пунктов этого плана**. При реальном завершении части значение меняется по той же формуле; число 90 не фиксируется навсегда.
- Процент не измеряет готовность всего калькулятора, полноту исходного большого аудита матрицы, подтверждённость тарифов или готовность выпуска. Обе маршрутные очереди завершены; повторять их ради новой нумерации нельзя.
- Отчёт указывает формальный процент, конкретные нерешённые причины/блокеры, фактическое число проверок текущей группы и наличие/отсутствие подтверждённого тарифа. Если число нерешённых причин ещё не посчитано, прямо указать это вместо придуманного знаменателя.

## Экономия контекста и запусков

Использовать `rg`, выборки JSON и чтение диапазонов. Для публикации большого файла разрешено прочитать его внутри скрипта транспорта, не выводя содержимое в контекст модели; полнота подтверждается Git blob SHA. Не перечитывать целые WORK_LOG/NEXT_STEPS, реестр инструментов или старые raw для восстановления короткого состояния.

STARTED commit требуется до длительных операций. Для короткого offline-разбора использовать один итоговый checkpoint с нужным evidence. После каждого завершённого шага сохранить commit/remote/readback. Для docs-only изменений проверять ссылки, формат и содержание; повторный широкий live-аудит или full build требует конкретной причины/обязательного gate. Автоматически запущенный CI указывать с наблюдаемым статусом, не объявлять успешным до завершения. При active/queued job не писать в ветку и не запускать второго writer. Обычное ожидание не сопровождать повторяющимися отчётами.

## Git CLI: проверенное ограничение среды

16.10.2026 выполнен безопасный `GIT_TERMINAL_PROMPT=0 git -c credential.interactive=false push --dry-run origin HEAD:refs/heads/fix/v3-missing-route-prices-2026-10-15`: exit 128, `fatal: unable to get password from user`. В текущей среде нет настроенного credential helper, GitHub CLI, GH_TOKEN/GITHUB_TOKEN, GIT_ASKPASS или SSH_AUTH_SOCK. Проверялись только наличие/факт настройки; секреты не выводились.

GitHub connector имеет подтверждённую запись в разрешённую ветку, но не предоставляет callable-возможности настроить credential helper/OAuth CLI или экспортировать свой токен. Поэтому обычная Git-авторизация сейчас **BLOCKED_BY_ENVIRONMENT_AUTH**; переносить токен коннектора или присылать токен в чат не требуется. После появления штатного безопасного входа в среду проверить push dry-run, затем использовать обычный Git. До этого использовать connector с проверкой родителя и SHA; не повторять неуспешную авторизацию на каждом шаге. Новую локальную работу начинать с фактического remote head, чтобы не создавать расходящиеся истории.

Эти правила не разрешают main/merge/Production/Android и не меняют требования к надёжности тарифов.
