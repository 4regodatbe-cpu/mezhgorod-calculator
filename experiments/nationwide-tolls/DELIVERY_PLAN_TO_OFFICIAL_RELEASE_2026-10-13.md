# План доведения нового калькулятора до официальной публикации

Дата: 2026-10-13. Статус: **план**, не отчёт о реализации или разрешение на публикацию. Область: новый V3 с тарифной матрицей платных дорог России, затем официальный веб-калькулятор и отдельно Android-оболочка.

## Цель и неизменяемое правило расчёта

Один допустимый маршрут с минимальным временем → только его геометрия → для каждой самостоятельной платной дороги своя пара въезда/конечного съезда → одна готовая цена этой пары из матрицы дороги на дату/профиль → простая сумма готовых цен разных дорог. Нет расчёта по километрам платной дороги и runtime-суммы промежуточных ПВП. Неизвестная цена одной обнаруженной дороги делает неизвестным полный дорожный итог; доказанно бесплатный маршрут даёт 0 ₽. Коммерческий тариф поездки считается отдельным слоем.

Основные договорённости: [свод правил](RULES_RECONCILIATION_DRAFT_2026-10-13.md), [текущий контракт](ALGORITHM_SPEC_2026-10-12.md), [решения](DECISIONS.md). Новые вопросы по отдельным продуктам закрывать по данным оператора/маршрута; при недостатке доказательств оставлять конкретный случай unknown и продолжать остальные дороги.

## Стандарт готовности к официальному выпуску

1. Все платные продукты из проверенного к дате выпуска реестра распознаются на контрольных маршрутах либо явно отмечены как непокрытые. Неизвестная цена никогда не превращается в 0 или в неполный итог. Цифровое покрытие по всей России показывается как фактическое количество проверенных продуктов/пар, без заявления «все цены уже известны» при открытых пробелах.
2. Основные пользовательские контрольные направления с несколькими дорогами, короткой/длинной платной поездкой и бесплатным маршрутом проходят реальные UI/API-проверки. Там, где цена объявлена подтверждённой, матричная пара, период, профиль и источник проверены для выбранного пути. Критический разрыв в таком направлении закрывается до выпуска, а не маскируется подсчётом другой дороги.
3. Полный тестовый и GitHub релизный gate, браузерные проверки и Preview относятся к одному release SHA. Релизный отчёт содержит конкретный список ещё неизвестных цен и принятое решение о допустимом покрытии. Пользователь видит эти ограничения до решения об официальной публикации.
4. У официального веб-выпуска подготовлены проверка живого домена и немедленный откат к зафиксированной прежней production версии. Android считается отдельным выпуском и имеет собственную проверку.

## Порядок работы: шесть крупных этапов

Каждый этап заканчивается собственным датированным файлом в `experiments/nationwide-tolls/stages/`, записью в append-only `WORK_LOG.md`, обновлением `docs/WORK_STATE.md` и `NEXT_STEPS.md`, коммитом и кратким отчётом. Записывать исходный/конечный SHA, что/как/зачем/для чего изменено, проверенные источники, команды с результатом, неудачи, ограничения и следующий шаг. Не помечать план выполненным до проверки его критерия.

### 1. Собрать одну достоверную ветку и зафиксировать модель тарифного продукта

**Работа.** Сверить актуальные GitHub-ветку V3, локальный аудит и старые PR по SHA/файлам; перенести только нужные проверенные изменения в одну рабочую release-candidate ветку без случайного переписывания V2. Составить машинно читаемый реестр самостоятельных платных тарифных продуктов: М-4, А-289, обходы, части М-11, М-12, ЦКАД, М-1/М-3, региональные дороги. Для каждого указать оператора, физические границы, матрицу, возможное пересечение с соседним продуктом и правило исключения двойного начисления. Зафиксировать точный вход компонента: выбранный route ID/геометрия, product ID, первая/последняя платёжные границы, дата/профиль и status.

**Где.** `national-registry.json`, `ALGORITHM_SPEC_2026-10-12.md`, `DECISIONS.md`, `lib/toll-engine/route-toll-composition.ts`, `lib/v3-calculation/*` (сначала аудит интерфейса; реализация следующего этапа). Отдельный отчёт `stages/01-baseline-and-product-boundaries.md`.

**Выход/критерий.** Одна воспроизводимая ветка с указанным GitHub base и SHA; все текущие известные платные продукты имеют уникальный ID и правило принадлежности, а неоднозначные — явный unknown. Для М-4+А-289 и сопряжённых обходов есть примеры, доказывающие отсутствие двойного начисления. Точный список файлов/коммитов для переноса известен; старые PR не подмешаны без разбора.

### 2. Очистить и наполнить готовую матрицу

**Работа.** Идти по реестру продуктов, начиная с дорог, уже встречающихся в пользовательских контрольных маршрутах. Для каждого продукта подтвердить класс I/без транспондера, пару границ, направление (если важно), цену/период и дату действия. Сохранять операторский источник и принятую пользователем проверку Яндекса как разные типы происхождения данных. Проверять будний и выходной профиль выбранного маршрута на одной и той же паре. Конфликты 428 М-4 ключей группировать по причине (граница, дубли старых цепочек, ошибочная колонка/профиль/версия); исправлять генератор/источник группами, а не выбирать произвольную из 428 цен. Не производить обратную цену из прямой без подтверждённой симметрии. Продолжить М-11 head/mainline/tail, М-12 Сокуры/Шали и другие восточные пары, ЦКАД 2 381/3 189 scope, М-1/М-3, А-289 и регионы.

**Где.** `TARIFF_VECTOR_MATRIX_2026-10-12.json`, `TARIFF_SELECTION_REGISTER.json`, `M4_REVIEWED_ENDPOINT_CELLS_2026-10-13.json`, `national-registry.json`, `scripts/build-vector-matrix.cjs`, `scripts/build-release-register.cjs`, `scripts/validate-vector-matrix.cjs` и источник каждого продукта. Отчёт `stages/02-matrix-and-source-audit.md` с таблицей покрытия.

**Выход/критерий.** Для каждой известной сети указаны число продуктов, проверенных пар и случаев unknown с причиной. В активной матрице нет двух разных сумм для одного точного ключа/даты/профиля; исторические спорные записи сохранены только для аудита. Каждая активная цена имеет источник, версию и проверенный scope. Генерация реестра повторяема, валидатор и quote-контракты проходят. Полноту всех платных дорог России не заявлять без проверенного перечня; каталог и открытые пробелы показывать честно.

### 3. Довести расчёт V3 до правила «пара каждой дороги → сумма дорог»

**Работа.** На одной выбранной геометрии определить полный набор платных продуктов. У каждого найти его первую и последнюю нужные платёжные границы, вызвать точный lookup готовой матрицы и получить один компонент. Затем один раз сложить готовые компоненты разных продуктов. Разделить объединённый `m4_a289`, убрать денежные legacy/per-PVP fallback из V3 и не терять отдельные обходы; подключить М-1/М-3/регионы при достаточном evidence. Любая обнаруженная неоплаченная/неразрешённая дорога блокирует полный итог. Подтверждённая бесплатность требует полной проверки маршрута. Коммерческая стоимость поездки остаётся отдельной и получает дорожную сумму только после полного результата. API/UI/копирование показывают применимый период и подтверждение именно из использованной матричной записи.

**Где.** `lib/v3-calculation/route-leg-pricing.ts`, `lib/toll-engine/route-toll-composition.ts`, матричные адаптеры в `experiments/nationwide-tolls/engine/`, `app/api/v3/calculate/route.ts`, `app/v3/components/*`. Отчёт `stages/03-v3-integration.md`.

**Выход/критерий.** Тестовые маршруты с одной, двумя и тремя разными дорогами дают ровно сумму соответствующих готовых ячеек. Цена не меняется от добавления промежуточного ПВП к уже найденной точной паре; изменение крайней границы требует другой ячейки. Нет двойного счёта М-4/А-289/обхода, а отсутствующий компонент возвращает `unknown/null`, не частичную цену. API и UI показывают то же значение и причину неизвестности.

### 4. Проверить реальные маршруты и обновить релизные проверки

**Работа.** Прогнать матричный генератор/валидатор, focused тесты каждого продукта, `npm run test:audit`, `pnpm lint`, `pnpm build` и финальный GitHub gate на одном SHA. Пересмотреть `scripts/segment10-production-readiness.mjs`, `.github/workflows/calculator-final-gate.yml` и `scripts/check-tariff-freshness.mjs`: сейчас они закрепляют `/v2` и старую дату `TARIFF_AS_OF=2026-10-02`; обновлять ожидания только вместе с фактическим переключением продукта и свежей матрицей. Провести реальные POST-контроли на выбранных геометриях в обе стороны/два профиля: короткая А-289, Крым→Москва с М-4 и отдельными платными объектами, М-4 длинная/короткая, М-11, М-12, ЦКАД, М-1/М-3, регионы, маршрут без платных дорог и путь с недостающей ценой. Сверять Яндекс только при совпадающих границах, дате, классе и направлении; цель ранее заданной точности расстояния ≤3% применять лишь к сравнимой геометрии. Проверить веб на телефоне/ПК, даты, копирование, ожидание и сбои провайдера; измерить время типового и дальнего расчёта.

**Где.** `scripts/*test.ts`, `experiments/nationwide-tolls/engine/*.test.mjs`, `.github/workflows/calculator-final-gate.yml`, релизные скрипты и сохранённые route controls. Отчёт `stages/04-end-to-end-verification.md` с таблицей «маршрут → обнаруженные дороги/пары → матричные цены → итог → контроль → статус».

**Выход/критерий.** На exact SHA зелёные все необходимые тесты, сборка, CI и браузерные проверки; нет ложной бесплатности, неучтённой платной дороги и частичного итога. Отклонения от сравнимого Яндекс-контроля исследованы по геометрии/тарифу, а не спрятаны подбором цены. Все известные непройденные случаи перечислены с причинами и явно не объявлены проверенными.

### 5. Выпустить тестовый Preview и принять релиз-кандидат

**Работа.** После локальных проверок опубликовать согласованную рабочую ветку в GitHub, подготовить отдельный PR с описанием продуктового правила, источников, покрытия, CI и рисков; старые PR №6/9/12 оценить по пересечению, не сливать автоматически. Получить Vercel Preview именно на зафиксированном SHA; проверить `/v3` и реальные запросы через UI/API, включая многодорожный маршрут, unknown и копирование. Дать пользователю ссылку на Preview и таблицу конкретных контрольных поездок для его проверки. Исправления повторять на новом SHA с повторным gate; после последней проверки зафиксировать release candidate и перечень остающихся unknown.

**Где.** GitHub release PR, Vercel Preview, `stages/05-preview-acceptance.md`, `docs/WORK_STATE.md`.

**Выход/критерий.** Preview READY на том же SHA, что прошёл финальные проверки; пользователь может посчитать и проверить маршруты. Есть принятый список тарифного покрытия и явных неизвестных, решение «готово к официальному веб-выпуску» относится к конкретному SHA. Preview сам по себе не является публикацией на официальном адресе.

### 6. Официальный веб-выпуск, Android и наблюдение

**Работа.** После прямого запроса на публикацию зафиксировать текущую production версию и способ отката; проверить фактическую production branch/domain. В release PR изменить официальный вход `app/page.tsx` на утверждённый V3, синхронно изменить статические проверки и CI, защитить V2 как предыдущий рабочий путь до успешного релиза. Проверенный SHA провести через разрешённый merge/release и развернуть на Production. На фактическом официальном домене проверить корень, `/v3`, `/api/version`, несколько реальных POST/результатов/копирований, мобильный вид и ошибки/время ответа. Если обязательный контроль не проходит — вернуть прежний production deployment и зафиксировать инцидент. После стабильного веб-выпуска обновить Android WebView, который сейчас указывает `/v2`, собрать APK через `.github/workflows/android-apk.yml`, проверить тему/навигацию/расчёт и распространять APK отдельным явно утверждённым действием.

**Где.** `app/page.tsx`, `.github/workflows/calculator-final-gate.yml`, `scripts/segment10-production-readiness.mjs`, `android-app-v2/.../MainActivity.kt`, Vercel deployment и `stages/06-official-release-and-monitoring.md`.

**Выход/критерий.** Официальный адрес отвечает новым калькулятором на зафиксированном SHA; реальные проверки совпадают с Preview, версия/источники указаны, откат проверяем и сохранён. Отдельно отмечено, выпущен ли новый APK: веб-публикация сама по себе не обновляет установленное приложение. После релиза продолжается мониторинг unknown, тарифных обновлений и новых операторов без обещания уже проверенных цен для всей страны.

## Правило перехода между этапами

Следующий крупный этап начинается после документа с результатами предыдущего и проверки его критерия. Неполную матричную цену не повышать до «подтверждённой» ради зелёного CI или релиза. Исторические аудиты/тесты повторно использовать как доказательство только на соответствующем SHA; на новой релизной ветке запускать нужные проверки заново. Первый конкретный шаг после утверждения этого плана — этап 1: сверить GitHub V3 HEAD с локальными четырьмя коммитами и составить единый реестр платных тарифных продуктов.
