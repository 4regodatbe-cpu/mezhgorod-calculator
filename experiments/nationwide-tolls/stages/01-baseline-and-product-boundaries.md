## Что сделано и зачем

Создан `tariff-products.json` — отдельный машиночитаемый каталог идентичностей тарифа, связанный с `national-registry.json` через `registryId`. Каталог перечисляет 23 самостоятельных либо требующих самостоятельной проверки продукта и один явно неразобранный агрегат (`pskov`, четыре участка). Он определяет границу по первой/последней доказанной платёжной точке на **выбранной** геометрии, матрицу для проверки и правило пересечения. Поля «to audit» не означают, что цена подтверждена. Оператор и первичный источник по `registryId` находятся в `national-registry.json`; отдельную дату/профиль и источник каждой цены хранит тарифная строка матрицы.

Ключ запроса компонента: `selectedRouteId`, `selectedGeometry`, `productId`, `firstPaymentBoundary`, `lastPaymentBoundary`, `departureAt`, `vehicleCategory`, `paymentProfile`. Одна точная готовая цена для пары каждой обнаруженной самостоятельной дороги; готовые цены разных продуктов просто складываются. Если доказательство проезда, граница, готовая строка или взаимное исключение не определены, **весь итог unknown**, без частичной суммы. Каталог пока не подключён к V3 runtime и не является тарифной матрицей.

| Сценарий | Компоненты | Защита от двойного счёта |
| --- | --- | --- |
| М-4 затем А-289 | `m4` + `a289` | М-4 строка не содержит А-289; две точные пары, две готовые цены. |
| М-4 затем А-289 через западный обход | `m4` + `a289` + `krasnodar-west-bypass` при доказанном проезде | Обход не входит в предыдущие две строки; неясная привязка даёт unknown. |
| М-11 от Москвы до 679 км и далее | `m11-15-58` + `m11-58-679` + `m11-679-684` по фактической геометрии | Не выдавать сумму первых двух как полную, пока третий продукт не привязан и не оценён. |
| ЗСД и ШМСД | Два ID с неразрешённым тарифным пересечением | До проверки правил оператора совместное начисление unknown. |

## Аудит действующего интерфейса

`lib/toll-engine/route-toll-composition.ts` всё ещё объединяет М-4 и А-289 в `m4_a289` и все региональные в `regional`. `lib/v3-calculation/m4-a289-composition.ts` уже отдельно получает M-4, A-289 и обход, но суммирует их **внутри одного runtime-компонента**; его A-289 локальные суммы и оценка обхода требуют отдельного матричного аудита. `lib/v3-calculation/route-leg-pricing.ts` передаёт `m1/m3/regional` с `tolls:null` и применяет legacy fallback. Эти факты объясняют, почему наличие нового каталога пока не делает V3 готовым к выпуску. Разделение runtime по `productId` и exact row относится к этапу 3 после аудита источников этапа 2.

Локальные коммиты после предыдущей audit-базы `bd95fcd`, требующие сверки с GitHub перед переносом: `fb50f8f`, `3ce9f4a`, `7cf40fb`, `22bffe7`, `47b045f`, `3059331`, плюс коммит данного этапа. `96e3aba` и `bd95fcd` находятся в локальной базе и тоже требуют проверки относительно GitHub дерева. Это список для сравнения, не доказательство отсутствия эквивалентных правок на GitHub.
