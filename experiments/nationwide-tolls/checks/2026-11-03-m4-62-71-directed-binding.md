## Тарифные колонки

В действующей четырёхколоночной таблице Автодора поля означают отдельно способ оплаты и период. Для текущего runtime-профиля `no_transponder`, категория I, выбраны **вторая и четвёртая** колонки (без транспондера): ПВП 62 — 220 ₽ пн–чт / 260 ₽ пт–вс; ПВП 71 — 400 ₽ / 500 ₽. Код `M4_DATA` уже содержит ровно эти пары; суммы не изменялись. Первая/третья колонки с транспондером (62: 220/240; 71: 310/450) не должны ошибочно трактоваться как weekdays/weekends.

Приказ №58 от 27.02.2026 вступил в действие 02.03.2026 и является исторической редакцией. В его скане строки представлены двумя колонками дней недели: ПВП 62 — 220/220 ₽, ПВП 71 — 310/400 ₽. Это другая дата и иное табличное представление, не текущие четыре колонки. Поэтому прежнее заключение «действующие 400/500 нельзя подтвердить по приказу №58» уточняется: **400/500 подтверждаются выбранными no-transponder cells текущей таблицы, предоставленными владельцем; приказ №58 не является основанием текущей ставки**. Получить текущую веб-страницу напрямую в этой среде не удалось (предыдущий ограниченный GET вернул HTTP 403); числовой cross-check основан на таблице, приведённой владельцем. Не заявляется, что источник заново скачан в текущем сеансе.

Для PVP 62 значение 220/260 относится к тарифной записи события 62, а не к факту проезда вдоль основного хода. Само близкое прохождение мимо узла или участка с `toll=yes` не создаёт платёжное событие.

## География и направленное событие

Использованы две сохранённые независимые Valhalla/M‑4 трассы из `source-snapshots/systemic-road-audit-2026-10-15/runs/`, плюс локальные запросы к OSM API от 2026-11-03 22:05 UTC. Краткая воспроизводимая фиксация связей, лицензии и объектов — [m4-pvp-62-71-directed-graph-2026-11-03.json](../../../toll-od-matrix/sources/m4-pvp-62-71-directed-graph-2026-11-03.json). Исходные OSM XML и какие-либо ответы/геометрия 2ГИС в репозиторий не добавлялись.

Контрольное окно A `[37.862552,55.280674]` → B `[37.933973,55.125436]` точно присутствует в сохранённой линии Москва→Воронеж (индексы 866–964; длина контрольного окна в ранее сохранённом плане — 18,2 км). Направленный анализ:

- **ПВП 62:** именованные узлы `1755090321` и `4598844673` находятся на односторонних OSM `secondary_link`/`toll=yes` съездах. Линия подходит к общему месту разделения потока (точка A/узел съезда), но по сохранённой полной trace не содержит платёжного toll-booth event ни для одного узла ПВП 62. Геометрическая близость узлов 124/160 м и пересечение общего узла развилки не являются проходом через платёжную полосу. Вывод: ПВП 62 для этого выбранного пути не тарифицировать.
- **ПВП 71, Москва→Воронеж:** полная выбранная trace содержит `3036681112`, way `523826063`, `edgeToll=true`, shape indices 934–935. OSM связывает этот узел с `highway=motorway`, `oneway=yes`, `toll=yes`; далее поток идёт по встречному направленному сегменту `523826062`. Это подтверждённое платёжное событие основного хода, а не приближение к центру ПВП.
- **ПВП 71, Воронеж→Москва:** обратная сохранённая trace содержит направленный узел `285903913`, way `523826061`, `edgeToll=true`, shape indices 158–159. OSM также помечает его `motorway`, `oneway=yes`, `toll=yes`. У открытой тарифной строки нет разных ставок по направлению; это одно событие, не двойное начисление.
- **Границы:** тесты берут сохранённую линию непосредственно до платёжной точки и после неё с полной trace без соответствующего события. Такие поездки не получают ПВП 71 только из-за близости к воротам.

Таким образом, для данного сохранённого окна есть ровно один платёжный event — ПВП 71. При категории I, профиле без транспондера это 400 ₽ пн–чт / 500 ₽ пт–вс по текущим приведённым владельцем ставкам. ПВП 62 не добавляется. Это event-level применение строки `m4-71`, **не тарифная разность и не вычисленный оператором отдельный endpoint-пакет 62→71**. Исследовательский endpoint adapter для пара `m4-62 → m4-71` остаётся `unknown`, поскольку это иная экспериментальная модель полного тарифного вектора; она не должна переопределять подтверждённое событие открытого ПВП в V3.

## Изменение логики и регрессии

`validateKnownM4Plazas` теперь трактует `complete=true` вместе с `boothEventCoverage="complete"` как исчерпывающее свидетельство для выбранной геометрии: положительный `edgeToll=true` подтверждает событие; отсутствующее событие или явный `edgeToll=false` отвергает начисление; запись с неуказанным edge status остаётся `unknown`. При полном отрицательном свидетельстве больше не запускается локальное map matching, которое могло бы превратить близкий конец маршрута/съезд в ложное начисление. При неполной trace прежний fail-closed fallback не меняется.

Добавлены/уточнены тесты для сохранённого окна 62→71, единственного события 71, тарифа будни/выходные, обеих направленных трасс и границ до/после ПВП. Утверждения проверяют сохранённые OSM/Valhalla материалы, не вызывают 2ГИС и не обращаются к live-маршрутизаторам.
