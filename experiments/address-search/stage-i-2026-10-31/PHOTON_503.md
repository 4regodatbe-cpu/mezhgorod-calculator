# Stage I2 — Донецк, HTTP 503 и cooldown

## Подтверждено

Сохранённый GitHub Actions run [41198667966](https://github.com/4regodatbe-cpu/mezhgorod-calculator/actions/runs/41198667966), исходники `c0e76eccfda0bf4fd8eeb5ac299c6da1242baa57`:

| Запрос | Фактический результат | Ошибки вариантов | features | Время |
| --- | --- | --- | --- | --- |
| Ростов | PASS | 1 HTTP 503 | 103 | 1205 мс |
| Красн | PASS, частичная выдача | 2 HTTP 503, 4 cooldown | 20 | 770 мс |
| Донецк | SOURCE_UNAVAILABLE | 4 HTTP 503, 3 cooldown | 0 | 274 мс |

Полный исходный CI log сохранён локально в `/workspace/fh4-publication-GbCAbV/special-final.log`; небольшой переносимый extract — `ci-address-observations.json` рядом. Source query budget 20 секунд не исчерпан. Отказ произошёл **до ранжирования**: collector не получил features. Это не браузерный сценарий и не GeoNames API: live_probe вызывает Photon collector напрямую.

`lib/photon-address-search.ts:photonSearchUrls` создаёт для каждого из этих запросов семь **вариантов одного origin** `https://photon.komoot.io`. Это не семь независимых серверов. `lib/photon-fetch.ts` превращает неуспешный HTTP status в `Photon 503`; 503 не повторяется как connect_timeout. `lib/photon-request-pool.ts` после трёх 503/429 за 15 секунд приостанавливает origin на 15 секунд. Ещё один уже выполняющийся запрос может вернуть четвёртый 503; три оставшихся queue items отклоняются локально. Cooldown не создаёт четыре HTTP 503, но может блокировать другие запросы к тому же origin. Успешные ответы сбрасывают серию; положительный кэш остаётся доступным.

`scripts/address-503-regression.test.ts`: четыре новых **offline** теста PASS / exit 0. Воспроизведены ровно 4×503+3×cooldown, отсутствие незавершённых tasks, перенос cooldown между запросами и восстановление после срока, сохранение положительных данных при одном 503. Контролируемый порядок завершения — один возможный сценарий, согласующийся со счётчиками; он **не доказывает фактический порядок** сетевых ответов CI. Порог/пауза/бюджет не изменены.

Новый реальный capture 31.10.2026: Донецк HTTP 200 / 1848 мс, оба исходных ID с правильными координатами, ДНР первым; при этом один вариант получил 503. Следовательно, город существует, отказ периодический и не является постоянным отказом ранжирования. «Красн» дал неполную выдачу без Краснодара, точный «Краснодар» — успешный ответ. Это не доказательство стабильности Photon или исправления всех Prefix-запросов.

## Не установлено / BLOCKED_EXTERNAL_SOURCE

Сохранённые CI-логи не содержат per-variant HTTP headers, response body и идентификатора удалённого backend. По ним нельзя определить, кем именно сформирован 503 (Photon, его edge или сетевой посредник), причину перегрузки/ограничения, конкретный backend и реальный порядок ответов. Не приписываем отказ Vercel, конкретному городу или сетевой политике без доказательств. Повторный широкополосный probe/новые запросы не выполнялись.

Обоснованного локального изменения приложения, исправляющего **удалённый HTTP 503**, не выявлено. Не увеличивали бюджет, не отключали cooldown, не добавляли повторов к тому же origin, не ослабляли assertions и не подменяли независимый источник ещё одним URL того же сервера. Независимый GeoNames-пилот уже существует; его настройки Production не менялись. Новый четырёхгородный snapshot остаётся OFF и не выдаётся за общий резерв Photon.

## Следующий безопасный шаг

Для установления серверной причины нужны существующие upstream/edge журналы с временем соответствующих запросов либо отдельная узкая инструментированная проверка HTTP headers/body/status по вариантам в среде исходного CI. Это не разрешение на повторный запуск: в этой сессии новых Actions/push нет. Пользовательское поведение опубликованного Preview на текущем локальном SHA проверить нельзя до отдельно разрешённой публикации. Не создавать share-ссылку и не менять защиту. Не объявлять этот внешний дефект устранённым по четырём контролируемым тестам или одному успешному capture.
